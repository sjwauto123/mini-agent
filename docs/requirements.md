# Mini Agent 需求分析

状态：需求分析初稿，尚未进入实现。

最新范围：用户已选择[精简交付方案 A](scope-mvp.md)。首版以满足原始功能要求为主；早期跨进程 CLI、生产数据库等实现建议及其测试方式由[精简详细设计](design.md)替代。用例仍作为验收依据，但不宣称未实现的多用户认证或生产功能已经通过。

后续评审说明：产品目标已明确为持续使用和扩展，第一批五项架构方向已获用户确认，见[架构决策记录](decisions.md)。本文中的 CLI、SQLite 等建议反映初稿，不代表最终选型；具体技术与方案需逐项提供候选并由用户选择。

## 1. 目标与范围

从零实现一个由 LLM 驱动、支持工具调用和多会话连续对话的最小 Agent。核心价值是清晰展示完整运行机制，并通过可重复测试证明其行为。

必须自行实现：Agent Loop、工具注册与调度、模型输出解析、会话管理、上下文组装与基础压缩、异常处理、执行追踪。

不使用 LangGraph、OpenHands、OpenClaw、PI 等现成 Agent 框架承载主流程。允许使用模型官方 SDK、HTTP 客户端、JSON Schema 校验库、数据库驱动和测试框架等基础库。

首版范围：单 Agent、文本对话、工具顺序执行、本地持久化、真实 LLM 接入与确定性模型替身测试。

首版不要求：多 Agent 协作、向量数据库、复杂长期记忆、浏览器自动化、分布式部署、完整账号登录系统、流式输出。图形界面不是核心验收条件。

## 2. 用户场景

### 2.1 直接对话与追问

用户说“我叫小林，这周负责支付模块”，随后问“我刚才说我负责什么？”。Agent 无需工具即可基于当前会话回答。

### 2.2 工具调用与追问

用户问“计算 125 * 8”，得到结果后说“再除以 4”。Agent 应理解前文结果，再调用 calculator，返回 250。

### 2.3 一次请求包含多个动作

用户说“查一下北京明天的天气，如果下雨就记一条带伞待办”。Agent 应先查询天气，再根据结果判断是否创建待办，最后汇总执行结果。这里的“明天”基于请求时间与会话时区解析。

### 2.4 同一用户多个窗口独立

用户 A 在窗口 1 查询天气、记录出行待办，在窗口 2 编写周报、记录工作待办。每个窗口创建独立 session_id；之后分别携带原 session_id 继续聊天。

两个窗口的历史消息、摘要、待办、指代对象和工具可变状态互不影响。应用重启后仍可恢复已有会话。用户 B 不得通过 A 的 session_id 读取或修改 A 的数据。

## 3. 功能需求

### FR-01 输入与结果

- 每次对话请求包含 user_id、session_id、message；Runtime 为请求生成 request_id。
- 新会话显式创建，返回唯一 session_id；恢复会话时提供既有标识。
- 空输入、未知会话、会话归属不匹配返回明确错误，不隐式切换到其他会话。
- 对话结果包含 request_id、session_id、status、answer；失败时附机器可读错误码。
- status 至少区分 completed、failed、limit_reached。已完成的工具操作即使后续失败也应如实告知。

### FR-02 核心 Agent Loop

1. 校验请求及会话归属，保存用户消息。
2. 读取当前会话状态，组装并按需压缩上下文。
3. 向 LLM 提供上下文及已注册工具的名称、描述、参数 Schema。
4. 解析模型输出，区分直接回答、工具调用、无效输出。
5. 对工具调用执行名称检查、参数解析及 Schema 校验，调用工具并记录结果。
6. 将工具调用及结果加入本轮上下文，让 LLM 判断继续调用还是结束。
7. 生成最终回复或受控退出，保存会话及执行记录。

工具选择必须来自模型输出；禁止在 Runtime 中用用户输入关键词硬编码路由。首次模型响应即可给出最终答案，不要求先调用工具。

首版每个模型响应只接受一个工具调用，多个动作通过多轮完成；收到多个调用时作为协议错误处理，不能静默丢弃其中的调用。

### FR-03 工具注册机制

每个工具声明：name、description、parameters（JSON Schema）和执行函数。注册表提供注册、查询、列举模型可用定义、执行入口。

- 重复名称或非法工具定义应在注册时失败。
- 调用前校验必填字段、参数类型及未知字段，错误可反馈给模型修正。
- Runtime 注入 user_id、session_id、request_id、tool_call_id 等执行上下文，不允许模型参数覆盖会话归属。
- 工具统一返回结构化结果：成功时包含 data，失败时包含 error.code、error.message、error.retryable。
- 新增工具只需实现并注册，不应修改 Agent Loop 的业务分支。

### FR-04 首版工具

建议实现四个工具，覆盖用户给出的天气与待办场景：

- calculator：参数 expression；支持四则运算、括号和负数；返回数值。限制表达式长度和复杂度，拒绝函数、属性访问及代码执行，不能直接使用不受限 eval。
- search：参数 query；首版使用确定性 mock，返回 title、snippet、source，并明确标记 mock。空结果是正常业务结果。
- weather：参数 city、date；首版建议使用确定性 mock，日期使用 YYYY-MM-DD。返回地点、日期、天气与数据来源；不支持的地点或日期应明确说明。
- todo：参数 action，以及按动作要求提供的 text 或 todo_id；支持 add、list、complete。待办按 user_id + session_id 隔离并持久化，不能由模型指定其他会话。

search 可 mock 是原始要求允许的范围；weather 使用 mock 是本方案建议，真实天气接口可在后续接入。mock 数据必须向用户明确标识，不能作为实时查询结果展示。

### FR-05 模型接入与输出解析

首版接入一个支持工具调用的真实模型服务，并使用模型替身完成离线自动化测试。模型接口与 Runtime 分离，替身不能成为实际演示中唯一的决策来源。

优先使用模型原生 tool calling：工具调用从结构化字段解析，参数字符串按 JSON 解析，文本最终回复从响应正文读取。内部统一映射为三类事件：final、tool_call、invalid。

- final 必须包含非空 answer。
- tool_call 必须包含调用标识、已注册工具名及合法参数；调用前的说明文字不视为最终答案。
- 空回复、截断输出、畸形 JSON、未知工具和多个工具调用都必须有明确处理。
- 工具存在时不能同时把同一响应判定为最终完成。

“提取思考过程”在本项目中落实为可选的简短 decision_summary，例如“需要先查天气，再判断是否创建待办”。这是供调试使用的决策说明，不要求获取模型隐藏的完整推理链，也不能作为业务执行依据。模型不提供该字段时不得伪造其思考过程。

工具调用、执行结果和最终答案是验收重点；需要解释某次行为时，可结合可选决策摘要与真实 trace 查看。

### FR-06 Session 管理

- Session 是独立对话容器；同一 user_id 可以创建多个 session_id。
- 会话持久化用户归属、创建/更新时间、历史消息、上下文摘要和必要工具状态。
- 客户端负责在对应窗口保存和传递 session_id；不能只靠 user_id 或进程全局变量关联历史。
- 所有历史、摘要、待办的读取和写入都校验会话归属。
- 不同 session 可独立处理；同一 session 的并发请求首版采用串行处理或明确返回 session_busy，防止历史顺序混乱。
- 首版 user_id 由可信本地调用方提供，不等同于完成了生产级身份认证。对外部署时需从认证身份获取 user_id。

### FR-07 上下文与追问

每次模型调用按固定顺序组合：系统规则、工具定义、会话摘要、近期完整对话、当前用户输入和本轮已发生的工具调用及结果。当前请求日期及时区作为可信元数据提供。

适合进入上下文的信息：

- 用户明确表达的目标、约束、事实和偏好。
- 最近用户问题与 Agent 最终回复，支持自然语言指代。
- 与当前任务有关的工具调用参数、关键结果和对象标识，例如 todo_id。
- 未完成任务、待澄清信息和会话摘要。

不必反复塞入上下文的信息：完整执行日志、耗时和堆栈、API 密钥、重复工具输出、冗长决策说明。决策摘要可放在 trace 中，默认不作为持续记忆。

工具返回内容属于外部数据，不能覆盖系统规则；例如 search 结果中的“忽略之前指令”应作为普通数据处理。

### FR-08 基础压缩与轮次限制

“最大轮次”指单次用户请求的 Agent Loop 上限，不是会话生命周期的消息总数。用户持续对话时，前一请求用尽预算不应导致以后都无法聊天。

建议初始配置，均可调整：max_iterations=8，tool_timeout_seconds=10，model_timeout_seconds=30，request_timeout_seconds=120；max_iterations 包含重试、协议修复所消耗的模型调用。

- 达到循环上限或请求时限时停止新操作，返回明确状态及已知执行进度，不编造完成结果。
- 输入预算按模型总上下文窗口扣除输出预留和安全余量计算，系统规则与工具 Schema 也计入预算。
- 首版使用保守的 token 估算；近期优先保留最近 4 个完整用户回合，但不能突破硬预算。
- 预算不足时，将较早的完整回合压缩为有长度上限的摘要，保留关键事实、任务状态、结果、对象 ID 和未解决问题。
- 工具调用与对应结果按完整组处理，不能留下悬空调用；当前执行链优先保留，不能随意截断正在执行的任务。
- 持久化历史与模型上下文分开：压缩输入不删除原始历史，摘要记录覆盖范围，避免重复汇入。
- 单条工具结果过大时，保留关键结构化字段并标注截断；完整结果可留在本地执行记录中。
- 摘要生成失败时回退到有界的完整回合窗口，并明确记忆可能不完整；仍超预算则返回 context_too_large，不提交已知超限请求。
- 若使用 LLM 生成摘要，摘要调用同样计入本次模型调用次数、时限和 trace，防止压缩自身形成无界循环。

压缩只保证验收场景中的关键状态保留，不承诺任意历史逐字回忆。无法可靠解析追问指代时应向用户澄清。

### FR-09 异常处理

- 模型请求：认证错误直接报告；限流、网络波动等暂时错误允许有限重试，受请求总预算约束。
- 模型输出：提供简短协议纠错反馈，让模型在剩余轮次内修正；持续错误则受控结束。
- 工具调用：未知工具、参数错误、除零、数据不存在和执行异常转换为结构化失败结果，允许模型解释或调整。
- 工具超时：返回超时状态。对有副作用的操作不能默认重试；超时可能意味着结果未知，不能谎报“未执行”。
- todo 写入按工具调用标识进行幂等保护，避免同一次调用被重复调度产生重复待办；新调用标识的独立操作不等于相同调用重试。
- 存储失败：不得返回“已保存”；部分成功必须说明哪些步骤完成、哪些未完成。
- 日志应便于诊断，面向用户的错误不泄露密钥、内部堆栈或其他会话内容。

### FR-10 Trace 与日志

至少记录 request_id、session_id、iteration、事件类型、时间戳和耗时。工具事件额外记录 tool_call_id、工具名、经脱敏的参数、结果摘要、状态和错误码。

需要覆盖请求开始、模型调用、响应解析、工具开始/结束、上下文压缩、重试、限制触发和请求结束。每次已开始的工具执行都应有可匹配的成功、失败或超时终态。

首版使用 JSONL 或数据库事件表均可。API 密钥不得写入日志；用户文本与工具原文只在必要的本地存储中保留，控制台日志优先使用摘要。

## 4. 建议技术边界

以下是待详细设计阶段定稿的建议，不属于用户指定的硬性技术栈：

- Python 3.11+，使用 asyncio 实现运行与超时控制。
- 官方模型 SDK 或普通 HTTP 客户端，不引入 Agent 框架。
- JSON Schema 校验库校验工具参数；SQLite 保存会话、消息、摘要和待办。
- CLI 作为首版交互入口，支持新建、列出、恢复会话；两个终端窗口可验证独立会话。若跨进程运行，不能仅依赖进程内锁处理同会话并发。
- pytest 负责单元测试与集成测试；接入真实模型的测试单独标记。

建议职责拆分为 Runtime、ModelAdapter、ToolRegistry、SessionStore、ContextManager、TraceRecorder 和交互入口。这里确定职责边界，不提前固定类名与代码目录。

## 5. 测试需求与验收场景

### 5.1 确定性测试原则

使用可脚本化的 Fake LLM 依次返回最终回复、工具调用或错误，断言 Runtime 的状态、模型输入、工具调用和退出条件。此类测试验证运行机制，不证明真实模型的理解能力。

真实模型使用独立烟雾测试验证 Schema 驱动的自主选择与追问。普通自动化测试不依赖网络或密钥；真实模型测试不得伪装成已执行的离线测试。

### 5.2 核心验收用例

1. T01 直接回复：普通问候得到答案，工具调用次数为零。
2. T02 calculator：输入带括号和负数的表达式，得到正确数值；注入代码与超复杂表达式被拒绝。
3. T03 search：返回确定性 mock 结果并标记来源；无结果时不编造资料。
4. T04 多步任务：固定天气为下雨，执行 weather 后创建带伞待办；不下雨时不创建。
5. T05 纯对话追问：先说明姓名与职责，再追问，模型输入中有可恢复的相关信息；真实模型能正确回答。
6. T06 工具追问：先计算 125 * 8，再问“再除以 4”，后续计算使用前文 1000，最终得到 250。
7. T07 同用户双会话：A/S1 与 A/S2 分别写入不同历史和待办，各自恢复后只能看到自身数据。
8. T08 跨用户隔离：B 携带 A 的 session_id 被拒绝，工具与存储均不发生越权读写。
9. T09 持久化恢复：关闭并重新创建运行实例，指定原会话仍能读取历史、摘要及待办。
10. T10 注册机制：新增测试工具后自动出现在模型工具定义中并可调用；重复名称和非法 Schema 注册失败。
11. T11 参数校验：缺字段、类型错误、未知参数不进入工具函数；合法修正后可继续。
12. T12 解析异常：覆盖空回复、无效 JSON、未知工具、截断输出和多个调用，有限修复后成功或明确失败。
13. T13 工具错误：除零、找不到待办和内部异常均返回结构化错误，Runtime 不崩溃。
14. T14 预算耗尽：模型持续请求工具时，在设定调用次数内终止；同会话下一次请求预算重新开始。
15. T15 压缩与追问：构造足够长的对话触发压缩，摘要保留目标、关键计算结果和 todo_id，之后能够继续任务。
16. T16 上下文完整性：压缩后没有悬空工具调用；系统规则、工具定义和当前任务仍存在，输入估算不超预算。
17. T17 极端长度：超长用户输入、超大工具输出、摘要失败时，触发预定截断、回退或拒绝行为。
18. T18 超时与重试：模型限流、网络错误、工具超时和请求总超时均按预算终止；认证错误不反复重试。
19. T19 副作用与部分失败：同一 todo 调用重复调度只创建一条；创建成功后模型失败仍能报告已创建，超时未知不能被报成确定失败。
20. T20 并发：不同会话互不阻塞或污染；同一会话并发按选定规则串行或返回忙碌，历史顺序一致。
21. T21 Trace：request_id 可串联全部步骤，工具开始与终态匹配，错误和压缩可定位，密钥不进入日志。
22. T22 外部数据边界：搜索结果包含伪指令，工具结果保持数据角色；真实模型烟雾测试检查其不会据此越权操作。
23. T23 状态准确性：数据库写入失败不得返回保存成功；已有成功工具操作不因最终回复失败被静默撤销或遗忘。

### 5.3 完成标准

- 以上强制需求均有实现与对应测试证据；测试不能只断言预设回复文本。
- 单元与集成测试通过，关键断言覆盖工具实际执行、上下文内容、数据库状态及 trace。
- 真实模型完成直接回复、calculator、search、天气与待办组合任务、两类追问的演示。
- 提供可复制的启动及测试命令、配置样例、两窗口会话隔离演示步骤和已知限制。
- 核心依赖中不包含承载主流程的现成 Agent 框架。

## 6. 待定事项与开发顺序

当前尚未指定模型服务、凭据、交互界面和天气数据源。建议默认采用 Python + CLI + SQLite、可配置的一个工具调用模型接口、mock search/weather。模型凭据在真实联调前配置，需求分析阶段不需要提供。

“思考过程”建议按 FR-05 的决策摘要验收；若评审要求显式字段，应在模型输出协议设计时固定，而不是依赖服务商私有推理字段。

后续按以下顺序推进：

1. 详细设计：明确模型适配协议、工具 Schema、数据结构、存储结构、预算与并发策略。
2. 最小纵向实现：用户输入 → LLM → calculator → LLM → 最终回复，附 trace。
