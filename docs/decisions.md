### D12 每次用户请求的摘要尝试上限：B，最多 2 次

次数指实际发往模型的摘要请求，失败和重试均计数，工具返回后再次触发也不重置；本地字段缩减不算模型摘要请求。与整个 Agent Loop 的总预算关系另行确认，不沿用旧草案中的 8 次限制。

- A：最多 1 次。成本和等待更少，但首次失败或后续工具输出增长时缺少第二次摘要机会。
- B：最多 2 次，推荐。可用于首次软级摘要后的一次强级摘要，或一次暂时故障重试；需要记录次数与前后输入大小。
- C：最多 3 次。应对多次增长更灵活，但延迟、费用和反复改写的风险更高。

已确认 B：每次用户请求最多 2 次实际摘要请求，失败与重试均计数，工具返回后不重置。不是必定用满额度。只有新增待处理内容、一次暂时故障、或调整压缩范围/目标时才尝试下一次；不在相同输入与相同策略下反复请求。额度耗尽并不直接导致失败，仍按已确认的容量规则及 D13 处理。

### D13 摘要失败或额度耗尽后的处理：B，有条件降级继续

- A：无法完成所需摘要就结束本轮，保留原历史并提示重试。行为清楚，但即使输入仍能容纳也可能中断使用。
- B：推荐。原上下文能容纳时继续使用；否则保留最后有效摘要、结构化状态及当前任务必要信息，按完整回合缩小历史窗口并投影工具结果。发生信息省略时显式标记，不把未摘要历史记成已覆盖。关键任务依据不在剩余上下文时应澄清或要求补充，仍无法构造有效输入才返回 context_too_large。
- C：暂停并让用户选择精简历史后继续、缩小任务或重试。用户控制更强，但打断操作，前后端需要支持暂停与恢复。

已确认 B。代价是较早的对话细节可能暂时不可见；这属于声明过的降级，不代表长期记忆永久丢失。摘要失败不覆盖有效旧版本。经过支持的缩减仍无法容纳有效输入才返回 context_too_large；不能因摘要调用失败或未达到 55% 目标单独判定超限。

### D14 单条输入本身过长：B，保存为会话文档并按需读取

该项仅处理当前输入，即使历史压缩完仍放不下的情况，不重开软、硬阈值方案。

- A：首版拒绝并保留用户输入，提示拆分或缩小范围。实现少、语义清楚，但长文使用不方便。
- B：保存为会话内文档，模型按需读取范围或查找内容，推荐。原文可追溯且支持后续提问；需要文档存储与读取工具，并不能保证一次覆盖全文。
- C：自动分块处理各部分再汇总。适合全文摘要或逐段检查，但调用成本较高，跨块依赖与结果合并复杂。

已确认 B，文档范围读取与查找能力纳入设计；分块格式、工具 Schema、大小限制另行确认。需要逐字覆盖全文的任务不能仅靠按需读取就宣称已完成，需明确覆盖记录，超出支持范围时说明限制。不得静默丢弃输入末尾或把全文替换成不等价摘要。

### D17 单份内容的接收与保存上限：B，10 MiB

以下限制针对一份解码后的文本或序列化结构化结果，以字节计算；MiB = 1024 * 1024 字节。不是模型上下文 token 上限，也不等于一次读取应返回的大小。

- A：1 MiB，可配置。资源需求低，适合小型文档；较大的结果更容易被拒绝或要求源工具分页。
- B：10 MiB，可配置，推荐作为初始值。容纳常见文本与中等规模数据，资源较可控；更大内容需要分页或调整限额。
- C：50 MiB，可配置。减少对大结果的拒绝；更依赖增量接收、索引和搜索资源控制。

所有方案均需在接收/生成过程中检查大小，不能先无限加载进内存才检查。超过上限的内容不报告为完整保存；用户输入应保留在客户端供调整，工具结果需明确不完整且准确区分已执行副作用。流式接收的实现、账户总配额、预览大小、读取预算另行确认。

已确认 B：单份解码后文本或序列化结果默认上限 10 MiB，可配置。该限额不代表允许把全部内容直接送入模型。

- B：默认 30 天，到期删除原文并保留过期标记。成本较可控；超过期限的追问无法再读取原结果。

### D19 文档与工具结果的读取接口：B，统一资源接口

- A：文档和工具结果分别提供读取与查找工具。各自描述直观，但重复 Schema 和实现较多。
- B：统一资源引用，提供 resource_read 和 resource_search，推荐。来源在元数据中保留，读取可复用并便于后续扩展；需要统一内容类型、定位和权限契约。
- C：只有 resource_read，按页或范围顺序读取。工具少，但定位长内容需要多次调用，不适合远距离追问。

B 的 read 支持文本范围或结构化记录分页，search 返回匹配片段及可读取位置，不代表引入向量数据库或语义检索。具体检索算法、参数 Schema 与首版格式支持另行确认。每次读取/查找验证用户与会话作用域，模型不能传入任意本地路径。

已确认 B：统一资源引用及 resource_read、resource_search 两个工具，文档和工具结果复用读取能力。

### D20-D21 工具预算：B，按比例分配并区分操作类型

确认依据：用户指出 token 限制应依赖模型窗口后，助手提供修订方案，用户明确选择“B”。

修订候选：A 所有返回按统一比例；B 按比例分配并区分概览、正文读取、查找；C 比例预算再叠加固定 token 上限。

已选择 B。外置触发和模型可见返回预算均基于当前模型的有效输入预算，不再采用先前固定的 1024/2048 token 上限。操作比例已在 D22 确认。

计算契约：B = 模型窗口 - 输出预留 - 协议开销 - 安全余量；R = B - 已有上下文；本次返回上限 = min(操作比例 * B, R)。已有上下文包含系统提示、工具定义、历史、摘要、当前输入和已有工具调用/结果；待加入的返回包装计入本次返回预算，避免重复扣减。

预算是上限，不是生成目标；内容短或用户只请求小范围时只返回必要内容，不填满预算。空间不足以容纳有用内容时，按已确认的流程压缩上下文并重新计算，不能无限缩小返回使读取无法推进。返回组装后仍执行软/硬阈值及容量检查，不能因为单次返回合规就忽略整体压力。

普通工具结果超过按比例计算的外置阈值，或当前剩余空间无法容纳时，使用已确认的外置保存及有界概览。资源读取/查找自身的响应直接分页或缩减片段，不再次外置生成新引用，避免引用循环。

概览与读取上限包含引用、位置、游标、状态和内容等完整包装。分页游标必须对应实际返回位置；长记录和长行要能够继续读取未返回部分，不能静默丢弃尾部。元数据与预览可以由程序构造，不隐式增加模型摘要调用。具体定位方式和最小有效读取规则另行确认。

已确认的单份 10 MiB 接收/保存上限继续有效；它是字节资源限制，与按模型窗口计算的 token 输入预算用途不同。

### D22 各操作的初始比例：B，1% / 10% / 2% / 10%

- A：0.5%、5%、1%、5%。上下文增长较慢，但同样内容可能需要更多读取调用。
- B：1%、10%、2%、10%，推荐作为初始配置。为查找与正文分配不同预算，平衡读取次数和上下文占用；连续大读取仍可能触发压缩。
- C：2%、20%、5%、20%。单次获得更多内容，但成本和上下文增长较快，更容易触发两级压缩。

这些比例不是实测最优值；先作为配置基线，后续根据实际模型、延迟和任务成功率评估。外置阈值针对原始返回大小，概览/读取/查找上限针对模型实际可见响应。无论选哪组，都受 D20-D21 的当前剩余空间、有效读取和整体验证规则约束。

已确认 B：概览上限 1%、正文读取上限 10%、查找上限 2%、普通工具结果外置阈值 10%，均基于有效输入预算 B，配置可调。当前剩余空间不足时仍走已确认的压缩与重新计算流程。

### D23 浏览器断开后的执行生命周期：B，服务端继续执行

已确认 B：保存 run 记录，提交返回 run_id，服务内执行器管理生命周期；页面关闭或断网不触发取消，重开可以查询进度与结果。

### D24 前端进度传输：A，HTTP 提交与 SSE 推送

- A：POST 提交操作，SSE 接收服务端事件，推荐。适合模型文本与工具进度的单向推送，基于 HTTP；需要事件编号、断线补发和代理超时配置，SSE 本身不保证持久化或去重。
- B：WebSocket 双向通信。适合高频双向消息和未来语音交互；连接管理、重连和鉴权实现更复杂。
- C：HTTP 轮询。部署简单，结果查询易调试；事件呈现有延迟，轮询频繁时请求量增加。

传输选择不等于已经确认逐 token 流式模型适配；SSE/WS 可以先承载阶段事件与完整回复，模型输出的流式支持需要另行设计。取消等命令通过独立 API 时与 SSE 兼容。

已确认 A：HTTP API 提交操作，SSE 传递进度和回复事件；事件编号、保存和重连补发的具体协议另行确认。

### D25 同一会话收到第二条并发消息：A，忙碌拒绝

- B：持久化按序排队，前一运行结束后再处理下一条。用户可连续发送；需要队列长度、取消和上下文读取时机规则，后续输入可能基于已过时预期。
- C：同一会话并行执行。等待少，但会出现历史写入、待办副作用及上下文快照冲突，需要明确分支或合并语义。

三种方案都保留不同会话独立执行的要求。A 的忙碌判断需要服务端原子保证，不能只禁用前端按钮；重复提交同一请求与独立的第二条消息应由幂等设计区分。数据库锁或状态约束的具体实现另行确认。

已确认 A：服务端返回 session_busy，不启动独立的第二个运行，前端保留草稿；不同会话可独立执行。

### D26 用户点击停止时的行为：B，协作式取消

- A：只停止后续步骤，等待当前模型或工具调用自然结束。结果较容易确定；停止反馈可能很慢，并继续消耗当前调用费用。
- B：协作式取消，推荐。记录停止请求，阻止新步骤，尽快取消可取消的模型/只读工具等待；写操作若已开始则确认提交、回滚或未知状态后终止。响应较快且不谎报撤销；需要取消中与未知结果的处理。
- C：将执行隔离在子进程，停止时强制终止。对卡住的本地计算更有效；引入进程管理，仍不能撤销远端已执行的操作，可能留下结果未知。

已确认 B：停止新步骤，尽快取消可取消的等待，并准确记录已执行、未执行或未知结果。

### D27 服务进程崩溃或重启后的任务处理：B，中断后显式继续

- B：标记中断、展示已完成及未知步骤，提供显式“继续”操作，推荐。用户可恢复目标，已确认成功步骤不自动重放；需要保存步骤结果并正确构建继续上下文。未知写入须先核实，不能直接再执行。
- C：自动按检查点恢复。用户干预少；需要执行权仲裁、可靠幂等、外部结果核实和恢复预算，复杂度最高。

B 的继续创建新 run，关联旧 run，利用已保存状态继续任务目标，不承诺恢复 Python 调用栈或精确续传模型响应。识别遗留运行须确认原执行者不再活跃，不能服务一启动就终止其他存活实例的运行。检查点、执行者识别与恢复状态结构另行确认。

已确认 B：显示中断进度，由用户点击继续后发起关联的新运行，已知成功操作不自动重放，未知写入先核实。

### D28 模型正文是否流式显示：B，按适配器能力显示

- A：仅推送阶段事件，完整回复产生后一次显示。适配与解析简单；长回复等待时缺少文字反馈。
- B：按适配器能力流式显示公开正文，结构化协议缓冲校验，推荐。原生工具调用模型的正文可增量展示；统一 JSON 协议与不支持流式的端点先完整接收，校验后显示。体验和协议可靠性兼顾；不同适配器显示节奏不同。
- C：所有支持流式的协议均增量提取答案字段，包括 JSON 协议。体验较统一；需要正确处理不完整 JSON、转义、截断以及之后出现的工具调用或协议错误。

B 中增量正文是未完成内容，不能在完整响应解析前标为最终答案；若同一响应后续出现工具调用，正文应归为操作说明。工具参数必须完整解析并校验后才能执行，不能按流片段提前产生副作用。中断时可保留未完成标记，不当成完整答案或推断成功。隐藏推理不进入前端正文流；摘要内部调用也不作为用户回复流。

已确认 B：支持的原生工具调用端点流式显示公开正文，JSON 协议及不支持流式的端点完整校验后展示。

- A：异步数据库访问，推荐。配合 FastAPI 和 asyncio，不在事件循环直接执行阻塞数据库 I/O；需要理解异步事务与连接生命周期，SQLite 写入仍受数据库限制，不因异步变成并行写。
- B：同步数据库访问，完整工作单元放到受控线程池。调用栈和调试较直接；需要线程容量管理，不能在 async handler 中直接调用阻塞查询。
- C：按模块混合同步和异步。方便兼容不同库；连接与事务边界更难统一，首版维护成本较高。

无论哪种，事务保持短小，不跨模型调用、用户审批等待或外部网络请求。具体驱动、池大小与数据库会话生命周期不在本项自动确认。

已确认 A：业务数据库操作通过异步访问层完成，不把阻塞数据库操作直接放入服务器事件循环。

### D34 首版业务工具与真实数据接入：A，六工具及模拟搜索/天气

resource_read 和 resource_search 已在 D19 确认，不参与删减。以下方案均包含 calculator 和 todo；search 是外部资料搜索，resource_search 是当前会话已存资源内查找，两者不同。

- A：calculator、todo、mock search、mock weather，加上已确认的两个资源工具，共六个，推荐作为首版交付范围。场景完整、无需搜索/天气服务凭据、离线测试稳定；实际查询资料和天气价值有限，必须明确标记模拟来源。
- B：同样六个工具，search 和 weather 都接真实服务。日常使用价值更高；需要选提供方并处理凭据、限额、网络和返回格式，联调范围更大。
- C：真实 search、mock weather，其余相同。兼顾资料查询价值与接入成本；仍需选择搜索服务，天气仍不能作为真实预报。

三个方案都要求实际 Agent 使用真实 LLM 自主决策，Fake LLM 仅用于确定性测试。选择 A 不自动承诺本轮再接真实服务，后续新增数据源需继续评审。

已确认 A：calculator、todo、mock search、mock weather、resource_read、resource_search 共六个工具。搜索和天气向用户明确标记模拟来源，不能声称进行了真实联网查询。

### D35 模型配置与选择范围：B，具名配置与会话选择

- A：全应用只配置一个端点和模型。配置与调试简单；不同会话不能选择不同模型，切换通常影响后续所有运行。
- B：具名模型配置，每个会话选择一个，推荐。支持不同会话使用不同模型，方便长期比较和扩展；需要配置管理、能力校验和运行快照。
- C：每轮由路由规则或模型自动选择模型。可能优化成本和任务表现；结果、数据去向及上下文预算变化更难预测，需要另外设计路由策略。

B 每份配置包括端点、模型 ID、密钥引用、原生工具/JSON 模式、流式能力、上下文窗口、输出预留和 tokenizer 信息，具体配置格式及密钥保存方式另行确认。不得仅凭模型名称猜窗口大小。一次 run 固定所选配置及预算快照，摘要使用该 run 同一个模型，延续 D05。

会话切换模型由用户主动发起，在下一次 run 生效，重新计算预算；运行过程中不静默切换端点/模型。首版可以只有一份实际可用配置，具体供应商、模型名及端点需要用户在联调前指定，不因批准配置机制就默认选择外部服务。

已确认 B。是否将配置编辑界面纳入精简首版见范围提案，不能据此假定已要求建设完整模型管理后台。

### D36 模型适配器的 HTTP 与 SDK 选择：A，httpx 精简适配

- A：使用 httpx 实现精简协议适配器，推荐。超时、错误与流处理可以显式控制，不依赖 Agent 框架；需自行维护请求字段、流事件和供应商差异。
- B：各供应商官方 SDK，加统一内部适配层。供应商协议支持较完整、减少部分解析工作；多个 SDK 增加依赖，默认重试、超时和类型差异需统一。
- C：第三方多模型客户端库，加自研 Runtime。模型覆盖广、接入快；增加中间层依赖，需核查它的默认转换、重试与模型能力映射，不能让其承载核心 Agent Loop。

三项都遵循已确认的原生优先及 JSON 协议兼容、统一内部事件和按能力流式显示。A 首版只实现联调目标需要的精简协议，不承诺任意供应商 API 开箱即用。具体协议配置与模型能力错误不得通过静默猜测或跨服务回退掩盖。

已确认 A：httpx 实现联调目标所需的协议适配，不使用 Agent 框架。

### D37 模型暂时性故障的处理：B，同端点有限重试

- A：不自动重试，失败即返回错误。调用成本可预测；偶发网络波动会中断任务。
- B：同一端点和模型有限重试，推荐。未输出可见正文且未产生可执行决策时，暂时网络错误、限流或服务端暂时故障最多追加 2 次尝试，退避等待并受整体 deadline 约束；提高可用性，但可能增加等待和供应商重复计费。
- C：配置备用模型并自动切换。可能提高服务可用性；会改变能力、数据去向和预算，需要独立批准备用配置及失败条件。

B 不重试认证失败、无效参数或能力不匹配；参数/协议纠错是独立预算，不等于网络重试。若流式正文已呈现后断开，首版将该响应标记未完成并报告中断，不静默从头拼接另一轮文本。工具动作只能在完整校验后执行，模型重试不能自动重放工具。

这里的最多 2 次是普通模型调用的追加尝试数，不是摘要调用上限。摘要始终受 D12 的每个用户请求最多 2 次实际摘要请求约束，失败/重试都计数，不能叠乘成更多请求。服务端等待建议与本地 deadline 需共同约束；具体退避参数和整体预算另行确认。

已确认 B：暂时故障最多追加 2 次尝试，受总预算和流式输出状态限制；不自动切换模型。
